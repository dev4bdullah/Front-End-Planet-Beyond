    How the routing works

    list.addEventListener("click", event => {
    // the click may land on text or an icon inside the button
    const trigger = event.target.closest("[data-action]");
    if (!trigger || !list.contains(trigger)) return;
    const { action } = trigger.dataset;
    const id = trigger.closest("li").dataset.id;
    switch (action) { ... }
    render();
    });
    • closest("[data-action]"), not event.target. If the button ever contains an icon or a span, the click target is that child. Reading event.target.dataset.action directly returns undefined and the handler silently does nothing.
    • data-action says what, data-id says which. The action lives on the button; the id lives on the row. One closest("li") connects them.
    • Early return, not a big if-chain. Clicks that hit the padding or the text exit on line two.

    Why it matters here specifically

    Listener per button One delegated listener
    100 rows × 4 buttons 400 listeners 1
    After a re-render all 400 must be re-bound nothing to do
    Forget to re-bind buttons silently stop working can't happen
    Removing a row listener leaks unless removed nothing to clean up

    Task 6 rebuilds innerHTML on every change, which destroys every element in the list. Per-button listeners would die with them. Delegation is what makes the render-everything approach viable.

    Events that don't bubble

    Delegation relies on bubbling. focus, blur, mouseenter and mouseleave don't bubble — use focusin, focusout, mouseover and mouseout instead, or pass { capture: true }. change and input do bubble, which is why the checkbox above works through the same handler.
